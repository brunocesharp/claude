# Contexto do Projeto — Marketplace de Skills para Claude Code

## Objetivo Geral

Criar um **marketplace de plugins** para o Claude Code que cobre o ciclo completo de desenvolvimento de software — do discovery ao deploy. Cada plugin agrupa skills relacionadas e é instalado via `/plugin marketplace add` + `/plugin install`.

---

## Visão do Ciclo Completo

| Fase | Objetivo | Saída |
|---|---|---|
| **Discovery** | Construção da ideia do projeto | Documentos com conceitos importantes do projeto |
| **Escopo** | Formalização do que será construído | `escopo.md` |
| **Especificação** | Detalhamento das regras de negócio com BDD | `spec-functional.md` |
| **Arquitetura (documentação)** | Estrutura do sistema no modelo C4 e decisões registradas | `arquitetura/arquitetura.md`, `arquitetura/decisoes/ADR-NNN-*.md` |
| **Direção de Arte** | Identidade visual do produto (cores, tipografia, grid, iconografia, estados) | `direcao-arte/fundacao.md` |
| **Plano de Execução** | Detalhamento das tarefas | `execution-plan.md` |
| **Entrega por stories** | Quadro de épicos e stories, uma story por vez (em construção) | `implementacao/sprint-status.yaml` |
| **Arquitetura .NET** | Geração de código Clean Architecture + DDD + CQRS | Entidades, Commands/Queries, Repositórios, Controllers |
| **Arquitetura Angular** | Geração de código das camadas Core/Feature/Shared | Services, Components, Stores |
| **Arquitetura Java** | Testes unitários Java a partir dos cenários BDD | Classes de teste por camada |
| **Documentação de Negócio** | Registro das regras de negócio do domínio | `docs/{projeto}/business/{area}.md` |
| **Artefato Homologação** | Gerar e publicar artefato de homologação | Relatório de deploy em staging |
| **Artefato Produção** | Gerar e publicar artefato de produção | Relatório de deploy + rollback |

**Status atual:** todas as fases acima já têm skills implementadas. O catálogo completo, com gatilhos e saídas de cada skill, está no [README.md](README.md). Fases ainda mapeadas e não implementadas: Especificação Não-Funcional e Refinamento (telas, API, modelo de dados) — ver Roadmap no README.

## Decisões de Design

- **Skills modulares** — uma skill por documento/entrega, em vez de uma skill única end-to-end. Isso permite usar peças isoladas conforme a necessidade.
- **Interação conversacional + geração de documentos** — Claude conduz perguntas por blocos temáticos e ao final gera os arquivos `.md` (ou código, no caso das skills de arquitetura).
- **Formato de saída** — Markdown (`.md`) para documentos de discovery/escopo/especificação; código-fonte para skills de arquitetura.
- **Público-alvo** — múltiplos perfis: Product Manager, Tech Lead, Desenvolvedor, Analista de Sistemas.
- **Distribuição** — este repositório é um **marketplace de plugins** do Claude Code (`.claude-plugin/marketplace.json`). As skills são agrupadas em plugins por fase/stack (`sdd`, `workspace`, `discovery`, `spec-plan`, `delivery`, `architecture-docs`, `architecture-dotnet`, `architecture-angular`, `architecture-java`, `business-docs`, `art-direction`) e instaladas via `/plugin marketplace add` + `/plugin install` (ou pelo Skills CLI, `npx skills add brunocesharp/claude`).
- **Setup do workspace (inspirado no BMAD)** — a skill `sdd-setup` (plugin `sdd`) faz o papel do `bmad setup`: pergunta só o que ainda não foi respondido (cada plugin declara suas perguntas em `sdd-setup/modules/<plugin>.toml`), grava em `_sdd/config.toml` (time) e `_sdd/config.user.toml` (pessoal) sem alterar valores existentes, copia os scripts Python para `_sdd/scripts/` e mostra status e próximo passo.
- **Estado determinístico** — como no BMAD, as skills não interpretam estado de cabeça: os scripts de `_sdd/scripts/` (`workspace.py`, `status.py`) leem, validam e mudam o estado e devolvem JSON. O andamento da entrega fica em `docs/{projeto}/implementacao/sprint-status.yaml` (story: `backlog → ready-for-dev → in-progress → review → done`, mais `blocked` e `dropped`), com as transições validadas pelo `status.py` e por um hook do plugin `sdd`.
- **Workspace com vários projetos** — as skills de documentação rodam numa pasta só de documentação que reúne vários projetos, cada um em `docs/{projeto}/`, com o índice em `docs/workspace.md`. Toda skill de documentação começa identificando o projeto (citado na conversa, ou escolhido na lista do workspace), lê o `docs/{projeto}/project-config.json` (nome, stack, repositório), criado pelo `discovery-init`, e a configuração do workspace em `_sdd/` (idioma, nível de detalhe, pasta de documentação).
- **Repositório de código separado** — o código de cada projeto fica no próprio repositório. A URL e o caminho local são coletados no `discovery-init` (podem ser "a definir") e usados pelas skills que leem código (`arch-c4` no modo Levantamento, `business-docs`).
- **Vários repositórios por projeto** — quando o código está em mais de um repositório, a skill `multi-repo` (plugin `workspace`) mantém `docs/{projeto}/repositorios.md` (papel, caminho, contêineres C4, contratos e deploy de cada um), mostra o panorama do Git de todos e coordena entregas entre repositórios (mesma branch, provedor antes do consumidor, estratégia para contratos incompatíveis). Só lê por padrão; clonar e criar branch pedem confirmação; commit, push e merge só a pedido.
- **Arquitetura em C4** — a documentação de arquitetura segue *The C4 model for visualising software architecture* (Simon Brown), com diagramas em Mermaid C4 (renderizam no GitHub e no VS Code sem ferramenta extra). Decisões ficam em ADRs, uma por arquivo.
- **Nome da skill = nome da pasta** — o `name` do frontmatter é igual ao nome da pasta, e as skills se citam por esse nome.

### No workspace de documentação (vários projetos)

```
meu-workspace/
├── _sdd/                             # sdd-setup: config.toml, config.user.toml, version.toml, scripts/
└── docs/
    ├── workspace.md                  # lista dos projetos
    ├── arquitetura/landscape.md      # visão de todos os sistemas (opcional)
    └── {projeto}/
        ├── project-config.json       # configuração lida pelas skills (discovery-init)
        ├── project.md
        ├── repositorios.md           # só com código em vários repositórios (multi-repo)
        ├── discovery/
        │   ├── vision.md
        │   ├── opportunity.md
        │   ├── assumptions.md
        │   ├── stakeholders.md
        │   └── success-metrics.md
        ├── escopo/{titulo-do-escopo}/
        │   ├── escopo.md
        │   └── discovery/            # cópias dos arquivos de discovery relevantes
        ├── especificacao/{titulo-do-escopo}/spec-functional.md
        ├── arquitetura/
        │   ├── arquitetura.md
        │   ├── componentes/
        │   ├── dinamicos/
        │   └── decisoes/
        ├── plano-execucao/{titulo-do-escopo}/
        │   ├── execution-plan.md
        │   └── mudanca-multi-repo.md # entrega em vários repositórios
        └── business/
```

O código de cada projeto fica no repositório dele; as skills de código (`architecture-*`, `angular-*`, `deploy-*`) rodam lá.
